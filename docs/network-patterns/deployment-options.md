# Multus deployment options

Before choosing attachment patterns, a few Multus-level decisions shape how everything else behaves. Full option semantics are in the [Configuration reference](../configuration.md); this page focuses on trade-offs.

## Thin vs thick plugin

| | Thin (`multus-daemonset.yml`) | Thick (`multus-daemonset-thick.yml`) |
| --- | --- | --- |
| Architecture | `multus` binary executed by the runtime per CNI call | Small `multus-shim` binary talks over a Unix socket to a long-running `multus-daemon` |
| API-server access | Each CNI call builds its own client from the kubeconfig | Daemon keeps a shared client and informers |
| Metrics | None | Prometheus metrics endpoint |
| Resource footprint | Lower when idle | Daemon uses memory continuously, but per-call cost is lower |
| Features | Baseline | Required for newer features such as DRA integration |
| Debugging | Logs per call (stderr / `logFile`) | Central daemon logs (`kubectl logs`) |
| **Recommendation** | Small clusters, simple setups, minimal moving parts | **Default for new deployments**, high pod churn, observability needs |

See [Thick plugin](../thick-plugin.md).

## `clusterNetwork` vs `delegates`

| | `clusterNetwork` (+ optional `defaultNetworks`) | `delegates` |
| --- | --- | --- |
| How the default network is referenced | NAD name, CNI conf name, directory or file path | Inline CNI config in the Multus config |
| Generated by `--multus-conf-file=auto` | Yes | No |
| Follows changes to the primary CNI config | Yes (re-read at each call / config watch) | No, you must regenerate |
| **Recommendation** | **Use this.** | Legacy and static setups only |

`defaultNetworks` attaches extra NADs to **every** pod except those in `systemNamespaces`.
- **Pros:** central policy, for example a mandatory storage or management network.
- **Cons:** every pod pays the setup cost, and a broken NAD breaks every pod on the node.

## Namespace isolation

`namespaceIsolation: true` restricts pods to NADs in their own namespace, plus `default` and any `globalNamespaces`.

- **Pros:** multi-tenant safety, so a tenant cannot attach to a privileged VLAN defined elsewhere.
- **Cons:** shared networks must be duplicated per namespace or placed in a global namespace.
- **Recommendation:** enable it in any shared cluster, and keep "public" NADs in a single dedicated namespace listed in `globalNamespaces`.

## Readiness indicator

`readinessindicatorfile` makes Multus wait for the default network to be ready, for example `/run/flannel/subnet.env` or the OVN-K / Calico config file.
- **Pros:** avoids a pod start storm with errors during node boot or CNI upgrades.
- **Cons:** if the file path is wrong, every pod on the node hangs in `ContainerCreating`.

## `auxiliaryCNIChainName`

This runs an additional chain of CNI plugins from a subdirectory of the CNI config directory for every pod. It is isolated from the default network's own chain.

- **Use case:** node-wide tweaks applied to all pods (sysctls, extra routes) without touching the primary CNI's config.
- **Constraint:** `clusterNetwork` must point to a **file**.

## Kubeconfig and RBAC

Multus needs read access to NADs and pods, and write access to `pods/status`, to publish `k8s.v1.cni.cncf.io/network-status`. The DaemonSets create this automatically. For manual installs, see [How to use](../how-to-use.md).
